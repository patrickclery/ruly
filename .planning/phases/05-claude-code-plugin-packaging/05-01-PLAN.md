<objective>
Add the `claude-plugin` output target, part 1: `ruly squash RECIPE -a claude-plugin` writes a valid Claude Code plugin directory carrying the manifest and the recipe's squashed rules as a skill, with an ownership marker, an overwrite guard, marker-gated clean, git-ignore support and a dry run. Plan 05-02 adds the remaining components (skills, commands, agents, hooks, MCP, script path rewriting); plan 05-03 documents and releases it as 0.4.0.

Decision IDs index the bullets of `05-CONTEXT.md` `<decisions>` in document order:
D-01 reuse `--agent` with value `claude-plugin`, no new command or flag; D-02 `-o` is the output DIRECTORY, default `./ruly-plugin-<recipe>/`; D-03 plugin `name` = recipe name, `version` = ruly gem version, `description` = recipe `description:`; D-04 skills to `skills/<name>/SKILL.md`, commands to `commands/`, subagents to `agents/<name>.md` with `model:` preserved; D-05 recipe `hooks:` to `hooks/hooks.json`, `mcp_servers:` to `.mcp.json` resolved from `~/.config/ruly/mcp.json`; D-06 scripts to `scripts/` with references rewritten via `${CLAUDE_PLUGIN_ROOT}`; D-07 verify always-on capability against plugins-reference; D-08 YES branch (emit through that mechanism); D-09 NO branch (squashed body as skill `<recipe>-rules`, notice, README finding); D-10 specs assert layout and `plugin.json` fields, run `claude plugin validate` when available; D-11 (discretion) `marketplace.json` only if trivial.

D-07 is settled by 05-RESEARCH.md (HIGH confidence, primary docs plus a local validator run): a plugin cannot ship always-on instructions. D-08 is therefore not implemented anywhere in this phase; this plan implements D-09 (rules skill + notice), plan 05-03 records the finding in README. D-11: `marketplace.json` is NOT generated (it needs an `owner.name` ruly cannot know truthfully, and publishing is deferred); plan 05-03 gives it one README line.

Discretion choices made here (gaps the decisions leave open):
- `author.name` comes from `git config user.name` and is omitted when unset. It mirrors the `claude plugin init` default and is what makes `claude plugin validate --strict` pass (D-10). Recipe names are used verbatim (D-03 "kebab-case" is a recommendation the validator only warns about), but must match `[A-Za-z0-9][A-Za-z0-9._-]*` without `..` and must not be a Claude Code reserved name.
- Ownership marker: `plugin.json` `metadata` is `{"generator": "ruly", "recipe": NAME}`. Claude Code does not read `metadata`; ruly uses it to decide what it may wipe or clean.
- `-o CLAUDE.local.md` (the Thor default) and a missing `-o` both resolve to `ruly-plugin-RECIPE`, the same "equals the default means not explicit" rule Phase 4 applies for AGENTS.md.
- `clean -a claude-plugin` needs a RECIPE or `-o DIR`; with neither it cleans nothing and says so. `--deepclean` keeps its current meaning (Claude artifacts in the project), as in Phase 4.
- `assumption-delta scan 5`: not detected. The writers gain an optional directory keyword whose default is today's path (add-alongside, nothing promoted), so existing output is unchanged.

Purpose: distribute a recipe in Claude Code's native plugin format instead of ruly-specific `.claude/` writing, without changing the default `.claude/` output.
Output: `Services::ClaudePlugin`, CLI routing for squash/clean, a `scripts_dir:` keyword on the bin copy, dry-run lines, fixture, unit and CLI specs.
