<objective>
Build the deterministic token benchmark: a Ruby harness under `bench/` that runs the real `ruly squash` on a committed fixture corpus and compares, per recipe, the ruly output against a load-everything concatenation and a native Claude Code layout, then writes `bench/results/tokens.json` and `bench/results/tokens.md`.

Decision IDs index the `<decisions>` bullets of `06-CONTEXT.md` in document order (CONTEXT has no IDs of its own):
- D-01: script under `bench/`, Ruby, tiktoken `cl100k_base` as in `Ruly::Operations::Stats`.
- D-02: per recipe compare (a) ruly squashed output, (b) all rules concatenated, (c) native always-loaded set (CLAUDE.md + `.claude/rules/` without `paths:`), skills counted by description only.
- D-03: committed fixture corpus under `bench/fixtures/` (no network), plus an optional run on the user's real rules repo, noted separately and not committed if private.
- D-04: output `bench/results/tokens.md` + JSON.
- D-05: compliance harness via headless `claude -p`, at most 10 tasks with deterministic checks (plan 06-02).
- D-06: two compliance conditions, recipe-scoped CLAUDE.local.md vs native rules + skills (plan 06-02).

- D-08: model default `claude-sonnet-5-5`, configurable (plan 06-02).
- D-09: `docs/benchmarks.md` with methodology, numbers, limitations (plan 06-03).
- D-10: README/site token-reduction wording replaced by the measured figure plus a link (plan 06-03).
- D-11 (discretion): fixture contents and task wording.
- S-01 (specifics): cite IFScale and Gloaguen et al. (and Chroma, per orchestrator) in the methodology (plan 06-03).

Discretion choices made here (D-02, D-11):
- Native mapping of the same corpus, one to one: a file under a `skills/` path segment is a skill, under `commands/` a command (both cost only `name: description` up front); a file whose frontmatter has `paths:` is a path-scoped rule (loads only when a matching file is opened); every other file is an always-loaded rule. Native floor = always-loaded rules + all descriptors. Native ceiling = floor + every path-scoped rule (all matching files opened). The ceiling column is extra, so a reader sees both ends of the native range.
- The ruly count includes the descriptors of the skills and commands ruly wrote, because Claude Code loads those descriptions up front in both layouts. Skill and command bodies are not counted on either side.
- Bodies are stripped with `Ruly::Services::FrontmatterParser.strip_metadata` (the function squash uses) and concatenated the way `SquashHelpers.write_sources` writes them (each body newline-terminated, one blank line between bodies), so load-all and native counts are measured on the same text shape as the squash output.
- Percentages: `reduction = (baseline - ruly) / baseline * 100`, rounded to one decimal; negative means the ruly output is larger.

Purpose: replace the self-reported token claim with a reproducible measurement (research "Strategic options" #3). Phase 6 needs nothing from Phase 5.
Output: `bench/` harness, fixture corpus, committed fixture results, specs.
