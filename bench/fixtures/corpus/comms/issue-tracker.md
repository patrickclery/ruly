# Issue Tracker

The issue tracker is the single source of truth for planned and in-progress work. If it is not in the tracker, it is not planned.

## Writing an issue

The title states the problem or the outcome in a few words. The description gives enough context for someone else to pick the issue up: what is wrong or missing, why it matters, and what done looks like.

- Bugs include steps to reproduce, expected and actual behavior, and the environment.
- Features include the user need and acceptance criteria written as checkable statements.
- Technical tasks include the motivation, so the issue can be reprioritized without asking the author.

## Status

Keep status accurate. Move an issue to in progress when you start, to in review when the pull request is open, and to done when the change is deployed. An issue that sits in progress for more than a week without an update gets a comment explaining why.

## Estimates

Estimate in relative points during planning. If an issue is larger than the team's agreed maximum, split it before starting. Do not change an estimate after work starts; record the actual effort in a comment instead, which helps the next planning session.

## Comments

Use comments for findings, decisions and questions. Edit the description when the scope changes, and note the change in a comment so watchers see it. Mention people only when you need them to act.

## Linking

Link related issues, the pull requests that implement them and any incident they came from. A linked chain from incident to fix to follow-up makes later investigations much faster.

## Closing

Close an issue with a final comment that says what was done and where. Duplicates are closed with a link to the issue they duplicate. Issues that will not be done are closed with the reason.

## Labels

Use the shared label set for area, type and priority. Do not create new labels for a single issue; propose new ones to the team so the set stays small enough to be useful in filters and reports.
